# cc-connect 微信客服接入 Codex 二次开发总体规划

> 版本：v1.1 | 日期：2026-10-08 | 状态：开发计划，待联调验收
>
> 上游项目：https://github.com/chenhg5/cc-connect
>
> 开发仓库：https://github.com/whysmx/cc-connect

## 1. 项目目标

在 cc-connect 中**新增微信客服（微信端入口）平台适配器**，把个人微信用户通过企业微信「微信客服」发来的消息交给现有 cc-connect 项目及 Codex 处理，再将回答发回微信。目标是继承现有企微机器人可复用的后端功能，尽量只改入口，不单独开发客服平台。

遵循：最小改动、优先复用、多项目通过现有配置、避免过度设计、不要破坏现有平台接入。

## 2. 已确认需求

| 项目 | 需求 |
| --- | --- |
| 用途 | 仅问答；Codex 可读取项目资料，但不应修改或执行写入型操作 |
| 用户规模 | 初期预计约 10 人，仅作为容量预估，不设置业务侧固定用户数量上限；不建设复杂多租户或计费系统 |
| 微信客服 | 企业微信有管理员权限；客服账号按需配置和增减，不设置固定数量上限（实际受平台及部署资源约束） |
| 人工接管 | 保留企业微信原有人工客服接管功能 |
| 部署 | 有外网的 Windows 服务器 |
| 项目对应关系 | 一个客服账号对应一个独立 cc-connect 项目；同客服下多用户读取同一份项目资料 |
| 会话、消息、后台 | 尽量复用 cc-connect 既有功能，不新增独立管理后台 |
| Codex 模型 | 保留现有第三方中转站配置，不要求使用官方直连 |

## 3. 总体架构

```text
个人微信用户
    │
    ▼
企业微信 · 微信客服（按需配置多个客服账号）
    │
    ▼
公网 HTTPS 回调入口
    │
    ▼
新增 platform/wecomkf/ 适配器
    ├─ 回调验证与消息拉取
    ├─ 消息解密、转换、去重
    ├─ open_kfid → 项目路由
    ├─ 人工客服接管状态
    └─ 微信客服消息发送
    │
    ▼
cc-connect Core / 多项目引擎（复用）
    │
    ├─ 客服 A → 项目 A → Codex → 工作目录 A
    ├─ 客服 B → 项目 B → Codex → 工作目录 B
    └─ 客服 N → 项目 N → Codex → 工作目录 N
```

部署初期采用**一个 cc-connect 进程、一个 HTTPS 回调入口，项目配置数量按实际客服账号增减**，不预设客服账号数量。多个项目不得重复占用同一个回调监听端口，应在适配层共享监听与路由分发。公网只开放所需回调，Codex 与本机管理端口不直接对外暴露。

## 4. 二开范围

### 4.1 直接复用

- Go 技术栈和平台 / Agent 分离的核心架构。
- `[[projects]]` 多项目配置、工作目录、项目提示词和现有模型配置。
- Codex Adapter、现有会话管理、任务生命周期及已有管理命令。
- 日志、既有 Web UI 与部署管理方式（如适用）。
- 现有可复用的文字 / 图片 / 文件处理机制，以微信客服官方实际能力为限。

### 4.2 必须新增

1. `wecom_kf` 平台类型（建议实现于 `platform/wecomkf/`；最终文件名遵循上游真实代码结构）。
2. 微信客服回调校验、签名和加解密，以及收到通知后拉取消息。
3. access_token 获取 / 刷新；使用微信客服所需凭证，不与智能机器人凭证混用。
4. 根据 `open_kfid` 选择项目；生成隔离的用户会话键。
5. 客服消息回复、错误重试、消息去重、必要拉取游标的持久化。
6. 人工接管状态识别与 AI 回复抑制。
7. 示例配置、接入说明及核心自动化测试。

### 4.3 不做

- 不重新开发 AI 引擎、对话存储、独立网关或坐席工作台。
- 不增加独立数据库、Redis、MQ、计费、多租户管理平台。
- 不默认实现微信客服不支持的卡片、按钮、逐字流式更新或无限制主动推送。
- 不修改原企业微信智能机器人平台的行为。

## 5. 账号、项目及会话映射

每个客服账号的 `open_kfid` 必须唯一映射到一个 `[[projects]]` 配置。客服账号与项目的数量从现有项目配置动态加载，新增或减少客服账号只需维护配置，不得在代码中写死数量或索引。启动时检测重复映射，并在配置冲突时停止启动或禁用冲突接入，不允许随机选项目。

同一个客服账号下的客户共享项目资料目录，但**不共享对话历史**。建议会话键：

```text
wecom_kf:{corp_id}:{open_kfid}:{external_userid}
```

会话键作为现有 cc-connect Core 的 SessionKey，不另建会话系统。回调消息 ID 必须去重；同一用户在不同客服下的会话也应分开。

对当前会话可沿用原有新建会话、终止任务等命令；查看其他会话、切换到其他人的历史会话、修改运行模式或工作目录等操作仅允许管理员。

## 6. 回调和回复流程

```text
微信客服回调 → 校验签名 / 解密 → 快速响应回调
    ↓
异步拉取消息 → 游标更新 / 去重
    ↓
判定客服状态与消息类型
    ↓
open_kfid 定位项目
    ↓
external_userid 定位会话
    ↓
cc-connect → Codex（只读回答）
    ↓
发送前再次检查人工接管状态
    ↓
微信客服 API 回复
```

避免在微信回调请求里同步等待 Codex 完成，保障微信端回调时限和故障恢复。必要状态允许沿用现有数据目录落盘；不能因进程重启无限重复读取或重复发送已回复消息。

回答优先采用**最终文本回复**，必要时按微信客服平台限制拆分；附件 / 多媒体仅实现 cc-connect 已支持且微信客服 API 允许的交集。明确区分客户提问、客服回复、状态事件，避免机器人回复再次触发机器人。

## 7. 人工客服接管

人工处理继续使用企业微信原有接待工作台，本项目只做状态衔接。

- 正常 AI 接待：新问题交给 Codex。
- 进入待人工或人工接待状态：停止向 Codex 分发后续客户问题。
- Codex 已运行时：回复前再次检查客服状态，避免 AI 与人工抢答。
- 人工结束后的恢复：按照微信客服平台允许的状态转换，联调后确定，不自行定时强制恢复。
- 在所有状态中保持微信客服原始的客户、客服账号与会话关联。

## 8. Codex 只回答模式

优先复用上游 Codex 适配器现有的 `backend = "exec"` 和 `mode = "suggest"`（最终以固定上游版本的真实选项及权限行为为准）。工作目录仅开放必要读取权限；禁止写入型 MCP、提交代码、删除项目文件、任意命令执行等能力。不能单靠系统提示词声明“只回答”。

第三方中转站的 base_url 和认证等按现有部署配置处理，任何密钥不得提交到 Git 仓库。

## 9. 配置示例（目标结构，**不是当前上游可直接运行的配置**）

```toml
[[projects]]
name = "客服项目1"

[projects.agent]
type = "codex"

[projects.agent.options]
work_dir = 'D:\AIProjects\project1'
backend = "exec"
mode = "suggest"

[[projects.platforms]]
type = "wecom_kf"

[projects.platforms.options]
corp_id = "YOUR_CORP_ID"
corp_secret = "YOUR_WECHAT_KF_SECRET"
open_kfid = "YOUR_OPEN_KFID"
callback_token = "YOUR_CALLBACK_TOKEN"
callback_aes_key = "YOUR_ENCODING_AES_KEY"
listen_addr = "127.0.0.1:8081"
callback_path = "/wecom-kf/callback"
```

其他项目按需追加相同结构的配置，各自设置项目与 `open_kfid` 映射，无需为新客服账号修改源码。企业级共享凭证和监听参数应在落地时做去重，所有适用账号共用相应回调监听，不为每个项目单独创建监听器。上述字段名均需在实现和源码结构确认后定稿。

## 10. Windows 部署

- 固定上游版本 / 提交 SHA，再在 fork 上开发；保留与 upstream 的同步能力。
- Windows 部署 `cc-connect.exe` 和 Codex CLI；使用固定、非交互式服务账户运行。
- Codex 工作目录、凭证路径、第三方中转站配置必须在服务运行账户下验证。
- 公网 HTTPS（反向代理）只将客服回调转发到 `127.0.0.1` 内网监听。
- 配置启动自启、异常重启、日志轮转、必要备份。
- 验证 Windows 下只读沙箱真实生效，尤其考虑 Codex / 平台差异。

## 11. 开发阶段和验收

| 阶段 | 主要工作 | 验收标准 |
| --- | --- | --- |
| P1 基线 | 固定 fork 基线，Windows 跑通原生 cc-connect + Codex | 指定项目资料可正常回答；第三方中转工作正常 |
| P2 单客服 | 回调、验签解密、拉取、文本回复、会话映射 | 单个微信客服从微信提问得到答复；用户之间不串上下文 |
| P3 多客服 | 共享回调、配置驱动的客服到项目映射、按需增加或移除客服配置、消息去重 | 任意已配置客服都进入对应项目；增加客服无需修改代码；重复事件不会重复回答 |
| P4 接管与部署 | 人工状态、回复抑制、错误重试、Windows 服务化、回归测试 | 人工接管时 AI 不抢答；重启后接入恢复；原平台不受影响 |

## 12. 测试重点

- 两位微信客户同时问同一个客服：项目文件共享，但聊天上下文隔离。
- 同一个客户分别问两个客服：进入不同项目 / 不同会话。
- 消息重复回调 / 拉取重试：不重复触发 Codex 和回复。
- Codex 较慢、异常退出、发送失败：正确超时、提示和恢复。
- 人工接管发生在 Codex 生成过程中：禁止迟到的 AI 回复。
- 权限测试：普通用户不能读取其他人的历史会话或修改服务器配置。
- Windows 重启：配置、登录状态、必要的消息游标可恢复。
- 上游企业微信智能机器人等其他平台回归不受影响。

## 13. 待官方文档和真实账号联调确认

以下能力不预先视为已实现：

1. 微信客服回调验签、消息拉取及 token / 凭证作用域。
2. 客服消息发送窗口、回复时限、文本长度、消息条数及媒体类型限制。
3. 微信客服人工会话状态转换和 AI / 人工恢复条件。
4. 微信端回复是否允许特殊格式、附件及有限的进度提示。
5. 企业微信控制台的账号权限、可用接口及回调所需公网 HTTPS 配置。

## 14. 完成定义

初期在一台 Windows 服务器上运行一个 cc-connect 服务；按配置接入微信客服账号，每个客服账号对应一个 cc-connect 项目，**不在业务代码中限定客服账号数量**；用户规模按实际需求和部署资源调整（初期预计约 10 人，并非固定上限）；微信问答及会话相互隔离；AI 只读取项目资料，不执行修改；人工客服可接管且 AI 不抢答；无需额外的用户管理 / 计费 / 客服工作台；现有其他平台保持正常。
